# S10-C 本机远程合成 Jev 实测报告

日期：2026-10-30。基于 `ed2adfe` 的 A/B 实现，按本轮独立 **30 次请求（含失败/重试）、0.10 美元、24 小时**授权执行。真实应用和第二台实体电脑按用户要求留待以后。

**正式题结果为 3/9 成功（33.3%），尚未达到稳定日常使用要求。** 简单题 3/3，中等题 0/3，复杂题 0/3。五次停止与低于 0.90 的模型置信度对应；另一次发现了许可期限重复扣时的实现缺陷，已修复并通过离线故障回归。原始实测成绩保留为 3/9，没有将修复后的离线结果替代真实成绩。

## 实际执行经过

1. 先完整演练 mock：预热及正式 9 题全部通过，0 次 hosted 请求；另验证续跑拒绝已开始任务、未知状态、审批变化和预算回退。
2. 第一次真实预热中的 hosted 请求在约 1.93 秒后中止，Engine 约 2.01 秒返回（完整工作流约 3.86 秒），结果 `FALLBACK / PROVIDER_DEADLINE`，0 步、0 个物理动作，9 道正式题尚未开始。此请求用量未知，保留 $0.003 预留。
3. 无 HTTP 的网络检查测得 DNS 约 21 ms、TLS 握手约 779 ms。单列的一项“只判断、不执行”诊断成功返回，约 1.025 秒，其中连接约 0.726 秒。它采用 10 秒诊断超时，未产生任何执行许可，也没有改动正式执行的 2 秒期限。第一次超时的精确根因仍未确认。
4. 验证旧账本没有动作、会话已关闭、正式题全为 NOT_RUN 后，在**同一持久预算**下继续这九道从未执行的题目。未重跑预热；新批次另存，原始失败记录未改。
5. 正式题结束后停止付费调用。累计 20 次请求，未耗尽额度。服务、临时证书和凭据已清理，测试身份已撤销，预算和动作账本保留。

真实链路为：CLI 或实际 SDK stdio MCP → 本地协调服务/Engine → loopback 双向 TLS 网关 → hosted `jev-1.14.0` → 签名回执 → 本机独立 Chromium。使用 `required_jev`，没有自动降级 mock。它是**一台 Mac 的本地远程链路测试**，不包含第二台电脑、VPN 或真实网站。

## 发现的计时缺陷及修复

网关原先在等待模型后，签发“剩余时长”；本地验证器却将这个剩余时长再次从最初请求起点计时，模型等待时间被扣了两遍。第 01 题模型响应约 1.757 秒、置信度 0.96，Engine 在约 1.864 秒时已返回 STALE_RECEIPT，仍处于原 2 秒窗口内。

修复后，网关签署原始请求的有效窗口，窗口起点固定为请求进入网关的时间；本地仍取原请求、快照和目标的单调期限最小值。没有从响应到达时重新给出 2 秒，没有延长原快照，也没有重新签署缓存回执。回执的 `issued_at_ms` 在该网关中表示有效窗口起点，不是签名完成瞬间。

回归测试设置 1,500 ms 窗口和 850 ms 模型延迟：旧实现稳定误报 STALE_RECEIPT，修复后接受仍有效的响应，并继续拒绝超过原 1,500 ms 或更短快照期限的响应；缓存内容保持完全一致。相关 TLS、签名和 Engine 定向测试 31/31 通过；最终完整离线回归为单元/核心 344/344、集成 51/51、安全 40/40，类型检查与 lint 均通过（测试集合有交叉）。**该修复只完成离线复测，未再次付费重跑正式题，不能声称真实成功率已经提高。**

低置信度问题没有通过降低门槛处理。下一步需要独立评估脱敏状态是否足够表达“错误已修正/表单可提交”，或接入已验证的受控主 agent 交接；现有数据不足以确认是哪一种能提高稳定性。
