# S11：同题同执行器的 direct / CLI / MCP 对照

基线：`d540f8b`。三条路径都在同一台 Mac、同一个进程内 Engine、同一个 BrowserAdapter、同一套签名回执/TTL/0.90 门槛和同一个 RemoteDecisionProvider 上运行。唯一改变的是调用入口：直接方法调用、真实 CLI 子进程、真实 SDK stdio MCP。CLI/MCP 使用同一个 coordinator。题库为 cancel / correction / form，seed=707，language=en，分别1/3/4步。

## 当前结论

**未发现 CLI/MCP 封装本身降低完成率的证据。此前历史成功率不适合直接比较：研究适配器和主流程的模型输入不同，而且新主流程存在两个期限/恢复相关缺陷。** 本轮确认并迁移了输入优化，实测又复现了所有入口共用的计步缺陷。

仍有边界：离线一致性可以固定模型输出；真实模型有随机性和网络波动。新增批准后已补齐三档旧/新投影 × 三入口的18个目标；每个组合仅一次，且分组顺序存在偏差，不能据此估计长期成功率或认定某个入口更好。

## 1. 入口一致性

| 离线条件 | direct | CLI | MCP | 规范化模型输入/状态轨迹 |
|---|---:|---:|---:|---|
| 旧投影、正常 mock | 3/3 | 3/3 | 3/3 | 同题逐步完全相同 |
| 新投影、正常 mock | 3/3 | 3/3 | 3/3 | 同题逐步完全相同 |
| 旧投影、固定低置信度轨迹 | 1/3 | 1/3 | 1/3 | 同一步停止 |
| 新投影、同样低置信度轨迹 | 1/3 | 1/3 | 1/3 | 同一步停止 |

这共36个离线目标。置信度轨迹是依据历史观测值构造的**确定性故障注入**，并非完整 API 响应回放；没有原始被拒绝 choice 的数据，不伪称精确重放。它证明入口和输入优化都不会绕过相同的安全拒绝。

比较时去掉随机 snapshot/candidate ID，保留候选顺序与完整描述、goal、summary。真实完整请求的随机安全标识仍不同。检查结果见 [parity-proof.json](parity-proof.json)，四组目录保存逐题结果和模型输入轨迹。此对照三条路径都使用同一个 TLS 网关，因而单独隔离入口因素；本地 provider 与远程 provider 的传输差异不在该对照因素中。

## 2. 已确认的输入差异与迁移

此前 S6 的真实模型校准曾验证：保留当前字段/选择状态、明确可见步骤、去掉填写相同值等无效候选后，独立校准从3/6变为5/6。原核心却只传 task、step、error 等少量标志，候选描述为 `fill email`、`click submit`，没有说明纠错后的状态或表单是否可提交。

现在主流程默认使用严格的 `fixture-v2` 投影：固定的任务说明、依据受信任适配器流程和当前观察派生的下一步语义、字段/选项是否符合目标的布尔值。候选明确说明“修正模拟邮箱”“旧错误消息仍存在但邮箱已经修正，可提交”等目的。保留取消候选；去掉确定已经满足的动作。没有添加原始字段值、原始 DOM 或隐藏 complete 评分字段。

这是**任务说明与进度指导的迁移**，不是仅修改文字装饰。`legacy` 模式保留旧输入用于对照；远程验证器分别接受严格的旧格式和版本明确的新格式，拒绝任意观察文本、错误任务说明和额外敏感字段。旧网关不支持新投影时会拒绝，部署时本地与网关应同时更新。六个公共工具未变。

## 3. 剩余额度内的真实同题测试

原批准最多30次，开始本轮前已用20次。本轮使用9次，累计29次，保守预留 $0.087，未修改原预算。此阶段之后用户追加批准了60次/$0.20，完整对照结果另列如下。

三条入口都执行同一个 correction、seed707、三步预算、新投影；按 direct→CLI→MCP 顺序运行。原始结果全部保留在 [live-rich-medium](live-rich-medium/rows.json)。

| 入口 | 结果 | 模型置信度序列 | 已完成物理动作 | 原因 |
|---|---|---|---:|---|
| direct | FALLBACK | 1.00 / 1.00 / 1.00 | 2 | STEP_BUDGET |
| CLI | SUCCEEDED | 1.00 / 1.00 / 0.98 | 3 | — |
| MCP | SUCCEEDED | 1.00 / 1.00 / 0.98 | 3 | — |

三者起始观察与候选语义相同；direct 因过期恢复再次观察了初始状态，后续实际请求轨迹与另两者不同。direct 首次网络响应约1.845秒，CLI/MCP 首次约0.482/0.284秒，顺序和连接复用存在影响。不能由这一轮断言 direct 更差。新投影没有复现此前纠错题的0.58–0.70低置信度，但样本只有三个，不足以证明低置信度问题已普遍解决，也不是同seed的旧投影真实配对基线。

## 4. 共用计步缺陷

直接调用的账本包含一个 `REJECTED_BEFORE_EXECUTION`、两个 SUCCEEDED，目标 steps 却为3。第一个动作已证明在真正操作前被检查拒绝，系统重新观察恢复，但此前就消耗了持久 steps 和循环次数，三步任务因此提前用尽额度。

根据响应接近TTL，期限耗尽是合理推测；原审计没有区分具体的前置拒绝子原因，因此不把它当作已确认的精确根因。确认的缺陷是：已证明未执行的动作消耗了额度。

已修复并完成定向回归：只有证明物理操作未开始的 `ExecutionNotStarted` 才退还目标计步与本轮循环次数；回执仍标记已消费、动作仍以 REJECTED 保留。最多两次过期恢复继续生效。已开始但结果未知的动作不得退还、重放或解除隔离。修复及回归结果以 [verification](verification/checks.json) 为准。

新增回归以三步任务第一次过期未执行为前提，最终保留一个 REJECTED 和三个 SUCCEEDED、steps=3，目标成功。重复未执行仍最多尝试三次后停止；UNKNOWN 仍消耗一步。该计步修复已用于下述完整实测，两种投影使用相同的修复后Engine；过期恢复本身还由确定性故障回归覆盖。

S10-C 已修复的“许可时长重复扣减模型时间”也保留回归。这两项均属于所有入口共享的实现，不是 CLI/MCP 单独的错误。

## 5. 追加批准后的完整同题对照

独立授权60次/$0.20/24小时，未重置原账本。三档 × 三入口，各一次，共18个目标。入口顺序按题轮转，让direct、CLI、MCP各有一次排第一。原计划先旧后新；实际顺序为旧组首题超时 → 新组9题 → 旧组剩余8题，不能宣称两整组严格按计划先后完成。两组均使用同一修复后Engine和0.90阈值，仅输入投影组合不同。

| 入口 | 旧投影 | 新投影 |
|---|---:|---:|
| direct | 0/3 | 3/3 |
| CLI | 1/3 | 3/3 |
| MCP | 1/3 | 3/3 |
| 总计 | 2/9 | 9/9 |

按题型：取消2/3→3/3，纠错0/3→3/3，四步表单0/3→3/3。旧组的direct取消为一次网络超时，不能归因于投影；另六次中复杂任务均因低置信度停止。排除该网络超时对应的配对后，剩余8组为旧2/8、新8/8，仅作敏感性展示，主分母仍各9。

旧组第一次网络超时后停止，原失败与停止记录保留；只补做此前从未开始的八题。补做入口验证原标记、严格账本、已关闭无隔离/UNKNOWN、已执行ID跳过及同一预算，不重发原未知请求。补做阶段允许继续其他独立的新题，鉴权错误及UNKNOWN物理动作仍停止；这是相对于最初停止规则的已记录执行调整。初始源码快照、冻结协议和结果均保留。

完整工作流p50/p95：旧2.227/2.672秒，新2.328/3.061秒。旧组多为提前停止，因此这些数不能解释为旧组完成得更快，也不构成computer use速度对照。原始结果：[旧组首次](paired-legacy/rows.json)、[旧组补足](paired-legacy-remaining/rows.json)、[新组](paired-rich/rows.json)；[统计汇总](paired-analysis.json)。

**在这个小样本中，主流程接入任务说明、进度与动作语义后，本轮完成数从2/9增至9/9；没有观察到CLI/MCP封装自身的负面差异。** 单次随机模型响应、网络冷热和分组顺序仍会影响结果，无法单独归因于某一个投影字段，9/9也不保证日常长期100%。
